# Контракт API для симулятора CGM

Документ описывает передачу измерений симулятором в backend CGM Assistant.
Он не задаёт интерфейс или внутреннюю структуру модуля симулятора.

## Адрес и формат

- Локальный адрес backend: `http://127.0.0.1:8000`
- Эндпоинты измерений принимают JSON с заголовком
  `Content-Type: application/json`.

## Отправка измерения

`POST /api/v1/readings`

Тело запроса:

```json
{
  "run_id": "demo-001",
  "source_index": 17,
  "measured_at": "2026-11-12T12:05:00+03:00",
  "glucose_mmol_l": 8.6
}
```

Поля:

| Поле | Тип JSON | Требования |
|---|---|---|
| `run_id` | строка | Не пустая и содержит хотя бы один символ, отличный от пробельного. Идентификатор запуска симулятора. |
| `source_index` | целое число | Неотрицательный индекс измерения внутри запуска. |
| `measured_at` | строка | ISO 8601 datetime с часовым поясом UTC offset или `Z`. Дата и время без пояса отклоняются. |
| `glucose_mmol_l` | число | Конечное число больше нуля, единицы измерения — ммоль/л. |

Неизвестные поля отклоняются. Строки с числами и булевы значения не считаются
числами.

### Ответы

- `201 Created` — измерение сохранено; тело ответа содержит измерение в том же
  формате, что и запрос.
- `200 OK` — пара `run_id` и `source_index` уже была отправлена с теми же
  данными. Возвращается существующее измерение без повторного сохранения.
- `409 Conflict` — для этой пары `run_id` и `source_index` уже сохранены
  другие данные.
- `422 Unprocessable Entity` — некорректный JSON или поле не соответствует
  правилам валидации.

Ключ повтора — пара `(run_id, source_index)`. При повторной отправке измерения
симулятор должен сохранять исходный `source_index`.

## Получение сохранённых измерений

`GET /api/v1/readings`

Возвращает JSON-массив измерений, сохранённых текущим процессом backend.
Добавьте `?run_id=demo-001`, чтобы получить измерения только одного запуска.
Для неизвестного запуска возвращается пустой массив. Результаты сортируются по
`source_index` по возрастанию; без фильтра запуски идут в порядке добавления.

Измерения сохраняются в рабочей SQLite-базе и доступны после перезапуска
backend. После успешного сохранения нового измерения отдельно запускается
демонстрационный анализатор; детали интеграции описаны в
[`ALGORITHM_CONTRACT.md`](ALGORITHM_CONTRACT.md).

## Получение событий анализа

`GET /api/v1/events`

Возвращает JSON-массив всех событий, созданных демонстрационным алгоритмом.
Используйте `?run_id=demo-001`, чтобы получить события одного запуска.
Неизвестный запуск возвращает пустой массив.

Каждая запись сохраняет `event_id`, `run_id`, `event_type`, `phase`,
`origin`, `priority_hint`, `started_at`, `ended_at`, `measured_at`,
`glucose_mmol_l` и `details`. `phase` принимает `started`, `ended`,
`interrupted` или `observed`. Для незавершённых событий `ended_at` равен
`null`. Завершение эпизода использует тот же `event_id`, что и начало.

События не являются уведомлениями. Для выбранных типов событий и фазы начала
отдельно могут создаваться информационные уведомления согласно
детерминированным правилам прототипа; подробности ниже. Алгоритм и его правила
исключительно демонстрационные и не заменяют и не подавляют штатные
предупреждения CGM.

События и состояние алгоритма сохраняются в рабочей SQLite-базе и
восстанавливаются после перезапуска backend.

## Получение информационных уведомлений

`GET /api/v1/notifications`

Возвращает JSON-массив уведомлений. Для одного запуска используйте
`?run_id=demo-001`. Неизвестный запуск возвращает пустой массив.

Формат каждого объекта:

```json
{
  "id": "stable-notification-id",
  "run_id": "demo-001",
  "event_id": "source-event-id",
  "title": "Наблюдение алгоритма: изменение показания",
  "text": "Алгоритм зарегистрировал демонстрационное событие. Значение измерения: 10.2 ммоль/л.",
  "created_at": "2026-11-13T09:00:00+00:00",
  "status": "unread",
  "acknowledged_at": null
}
```

Сейчас уведомление создаётся только для событий фазы `started` типов
`demo_above_range`, `demo_below_range`, `demo_rapid_rise` и `demo_rapid_fall`.
Тип `data_gap` с фазой `observed`, фазы `ended` и `interrupted`, а также
неизвестные типы остаются только в журнале событий. Для независимых событий
уведомления создаются отдельно. Идентификатор исходного события защищает от
дублирующего уведомления при повторной обработке; повтор уже сохранённого
измерения анализатор не запускает.

Текст уведомления описывает демонстрационное наблюдение и показание. Он не
содержит медицинских рекомендаций и не отражает доставку push-сообщения.

## Подтверждение ознакомления

`POST /api/v1/notifications/{notification_id}/acknowledge`

Успешный ответ `200 OK` возвращает полный объект уведомления с `status: "read"`
и временем `acknowledged_at`. Повторный запрос безопасен и сохраняет время
первого подтверждения. Для неизвестного идентификатора возвращается `404`.

Уведомления и подтверждения сохраняются в рабочей SQLite-базе и доступны после
перезапуска backend. Они предназначены исключительно для демонстрационного
прототипа.

## Исторический CSV-симулятор

Локальный модуль `simulator` отправляет измерения в `POST /api/v1/readings`,
сохраняя только поля этого контракта: `run_id`, `source_index`, `measured_at`
и `glucose_mmol_l`. Предварительно вычисленные CSV-поля `Anomaly_Type` и
`Action_Recommended` не отправляются.

CSV с наивными датами требует явного часового пояса при запуске симулятора.
Исходный интервал между измерениями сохраняется в `measured_at`; параметр
скорости меняет только задержку между HTTP-запросами. При `200` и `201`
измерение считается обработанным, конфликт `409` и сетевые ошибки сообщаются
явно и не продвигают индекс источника.

## Формат ошибки валидации

Некорректный запрос возвращает HTTP 422 и стандартный для FastAPI массив
ошибок в поле `detail`, с указанием проблемных полей. Например:

```json
{
  "detail": [
    {
      "type": "greater_than",
      "loc": ["body", "glucose_mmol_l"],
      "msg": "Input should be greater than 0",
      "input": 0
    }
  ]
}
```
