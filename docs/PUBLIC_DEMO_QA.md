# Проверка подготовки публичного демо

Дата: 14 ноября 2026 г. Ветка: `feature/public-demo`, база — `main` / `origin/main`
`03773ddbd0f314860fa3039807654f60f39e25a7`. После первоначального сбоя DNS
повторный `git fetch origin main` успешно подтвердил совпадение.
Commit, push, merge и публичное размещение не выполнялись.

## Автоматические проверки

| Проверка | Результат |
|---|---|
| Backend и симулятор, включая public_demo | 74 теста, успешно |
| SQLAlchemy-модели | 42 теста, успешно |
| Исходный анализатор | 16 тестов, успешно |
| TypeScript + Vite локально | успешно; локальный Node 20.12 выдаёт предупреждение о версии |
| TypeScript + Vite внутри Docker, Node 22 | успешно, без этого предупреждения |
| Окончательный Docker build | успешно |
| `git diff --check` | успешно |

Первый backend-прогон внутри sandbox не смог открыть HTTP-порты. Итоговый
успешный прогон выполнен с разрешёнными локальными портами. Все тесты
использовали test-mode, собственные временные SQLite или in-memory базы.
Рабочий `data/cgm_assistant.sqlite3` не открывался и не использовался.

Новые восемь интеграционных тестов проверяют:

- атрибуты cookie и bootstrap; отсутствие доступа через чужой Origin,
  Origin:null, cross-site Fetch Metadata и запрос без специального заголовка;
- параллельные независимые посетители, управление собственным контроллером,
  выборки с чужим run_id и без фильтра, историю и чужой notification ID;
- идемпотентное подтверждение, перезапуск симуляции с новым run_id;
- повторный клиент с той же cookie, рестарт backend и сохранение подтверждения;
- удаление только тестовой SQLite между остановкой и новым запуском приложения,
  отклонение старой cookie и выпуск нового пустого сеанса;
- лимиты активных симуляций, частоты старта, числа сеансов, хранения истории
  и удаление истёкшего посетителя;
- синтетический сценарий: одно первое уведомление, подтверждение, новое
  ухудшение, отсутствие повторов при постепенном восстановлении;
- раздачу index.html, health и корректные 404 вместо frontend для неизвестных
  API, исторического CSV и путей исходников.

## Docker и реальные HTTP-запросы

Docker Desktop, Linux arm64. Контейнеры запускались с ограничениями 512 МБ RAM
и 0.1 CPU, без volume и без локального data/. Порт — только localhost.

Первый запуск выявил отсутствие корня проекта в Python import path; это
исправлено `PYTHONPATH=/app`. Исправленный и окончательный образы успешно
запускаются с новой пустой SQLite.

Через настоящий HTTP проверены:

- корневая страница, JS/CSS assets и `/health`;
- два одновременно запущенных независимых сеанса; полные 40 измерений у каждого;
- пауза одного посетителя при продолжающейся симуляции другого;
- resume, stop, завершение, новый run_id и сохранение собственной истории;
- события, получение уведомления, «read» после acknowledge, запрет чужого ID;
- пустые ответы на чужой run_id и изоляция выборок без run_id;
- отклонение cross-origin POST и прямой загрузки измерений;
- сохранение cookie, остановленной позиции, истории и подтверждения при обычном
  рестарте контейнера с сохранным файлом;
- удаление только `/tmp/cgm-public-demo.sqlite3` внутри тестового контейнера
  и следующий restart (повторено также на окончательном коде): старый cookie получает 401, bootstrap заменяет его,
  начинается пустой сеанс, новая симуляция доходит до всех 40 точек.

Подтверждение в HTTP-скрипте означает вызов того же API, что использует кнопка
«Я увидел». Секреты тестовых cookie не выводились в отчёт или логи команд.

При жёстком ограничении CPU один ускоренный прогон ×3600 превысил 12-секундный
таймаут тестового ожидания; обе симуляции затем завершились с 40 точками.
Частый опрос тестового скрипта был существенно интенсивнее штатного polling
Dashboard. Это не считается успешным соблюдением ускоренного таймаута.
Отдельный полный прогон ×60 на окончательном коде для двух посетителей занял
171,1 секунды. У подтвердившего посетителя создано 4 уведомления, включая
новое быстрое ухудшение после подтверждения; оба запуска завершились с 40
измерениями. Скорость ×60 укладывается в целевые 2–3 минуты в этом прогоне.

Проверка показала, что Docker health check с timeout=5s под 0.1 CPU иногда
не успевает запустить отдельный Python-процесс, хотя HTTP API отвечает.
В окончательном Dockerfile timeout увеличен до 20s, start-period до 60s.
Образ пересобран; новый контейнер под тем же лимитом CPU достиг состояния
`running healthy`, два последовательных health check завершились с ExitCode=0.
На холодном старте до готовности зафиксированы ожидаемые connection refused
внутри периода запуска. Render использует отдельную внешнюю HTTP-проверку `/health`.

После двух симуляций в одном измерении Docker stats показал около 69 МиБ из
512 МиБ. Это отдельное наблюдение, не измерение пика и не гарантия вместимости
для 8 активных посетителей или 64 открытых сеансов.

## Проверка состава сборки

Окончательный build context экспортирован отдельной scratch-сборкой с тем же
`.dockerignore`: 53 разрешённых файла. Проверено отсутствие `data/`, реальных
CSV, SQLite, `.env`, ключей, архивов, Git, virtualenv, node_modules, локального
dist и pytest cache. Единственный CSV — `demo/synthetic.csv`.

Свежий окончательный образ проверен без старта приложения: 37 файлов в /app;
только синтетический CSV, без локальных БД, секретов, реального датасета и
служебных файлов macOS. `/tmp/cgm-public-demo.sqlite3` в образе отсутствует:
он создаётся только при запуске. Синтетические числа составлены вручную;
исходные измерения Кристины для сценария не читались.

## Непроверенные области

- Browser не удалось подключить из-за ошибки его среды. Настоящие клики,
  отрисовка графика и refresh страницы в браузере в этой задаче не проверены.
  Проверены API, production-сборка и выдача frontend assets. Новый HTTP-клиент
  с той же cookie проверяет серверное восстановление, но не заменяет проверку
  поведения React при перезагрузке или потере БД в открытой вкладке.
- Render не создавался. HTTPS, proxy headers, фактический холодный старт и
  квоты конкретного аккаунта нужно проверить после согласованного размещения.
- Локальный контейнер имеет arm64 архитектуру. Сборка и запуск amd64 отдельно
  не выполнялись; Render соберёт Dockerfile для своей платформы.
- Не выполнялись длительный стресс-тест, реальная нагрузка на все 8 активных
  симуляций, 64 браузера и принудительное исчерпание памяти.
- Python зависимости сохранены с существующими диапазонами версий; будущая
  сборка может получить новые совместимые версии. npm использует lock-файл.

Тестовые контейнеры остановлены после завершения проверок.
