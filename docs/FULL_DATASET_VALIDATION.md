# Сквозная проверка полного датасета

## Условия проверки

- Проверка выполнена в локальной ветке `feature/full-dataset-validation`.
- Источник: `data/kristina/cleaned_glucose_data.csv`; в него вошли все 10 881
  строки измерений, после сортировки `source_index` непрерывен от 0 до 10 880.
- Временные метки CSV не содержат часового пояса. Для этого технического
  прогона им явно назначен UTC. Это тестовое допущение, а не установленный
  исходный часовой пояс данных.
- FastAPI работал с новой временной базой
  `/tmp/cgm-full-validation.sqlite3`.
- Алгоритм и его демонстрационные правила не менялись: вход в нижний диапазон
  при `<= 4.0 ммоль/л`, вход в верхний при `>= 10.0 ммоль/л`; выходные пороги
  `4.4` и `9.6 ммоль/л`; скорость тренда `0.25 ммоль/л/мин`, подтверждение
  тренда за два интервала; разрыв данных — более 15 минут. Эти значения
  предназначены только для демонстрационного прототипа.

## Сравнение с предварительным отчётом Кристины

Предварительный `final_report.csv` сообщает: TIR 84,6%, TBR 1,0%, TAR 14,4%,
1 678 «Dumb app notifications», 102 «Smart app notifications», 27 гипо- и
75 гипер-эпизодов, 188 аномалий и 30 заблокированных артефактов сенсора.

Эти метрики нельзя напрямую приравнивать к результату CGM Assistant:

- В предварительном отчёте границы вне диапазона — строго `<70` и `>180
  мг/дл`; так получено 1 678 отдельных измерений вне диапазона. Его
  «Smart app notifications» — 102 эпизода, сгруппированных отдельно для
  низких и высоких значений при промежутке до 30 минут.
- В проекте используются демонстрационные пороги `<=4.0` и `>=10.0
  ммоль/л` с гистерезисом и состоянием алгоритма. По этим входным порогам
  было соответственно 157 и 1 631 измерение. Это количество измерений, а не
  количество событий или уведомлений.
- 123 уведомления CGM Assistant состоят из начал событий диапазона и трёх
  подтверждённых быстрых снижений. Это иной набор правил и иной объект
  подсчёта, чем 102 сгруппированных эпизода предварительного отчёта.

Поэтому процент «снижения уведомлений» для этих двух систем не вычислялся:
сопоставимой базовой модели и одинаковых правил подсчёта нет. Результат не
является клинической оценкой эффективности и не доказывает медицинское
снижение числа предупреждений.

## Замечание о рабочей SQLite

Основной прогон использовал отдельную временную БД. Однако первое выполнение
backend-тестов запустило их тестовый FastAPI без `CGM_DATABASE_URL`, поэтому
13 тестовых запусков попали в `data/cgm_assistant.sqlite3`. Они были точно
идентифицированы по синтетическим именам и временной метке, сохранена
временная резервная копия, затем удалены с проверкой внешних ключей. Все
остальные строки таблиц совпали с этой копией после исключения тестовых
запусков. После сверки временная резервная копия удалена. Backend-тесты
повторно прошли с отдельной тестовой SQLite.

До запуска тестов SHA-256 рабочей БД был
`6a3f5c4a9305f724afdfc552fc4ae95eec34bc70e88ce09adc1ed92245190109`;
после удаления тестовых записей он стал
`a1c0c45ed8204d49723d40bc516c47f240904ae57e26f4c85171a480e0ccb0e8`.
Точных побайтовых копий состояния до тестов не было, поэтому идентичность
файла подтвердить нельзя. Утверждать, что рабочий SQLite-файл не изменялся,
нельзя; это ограничение проверки.

### Исправление изоляции тестов

Причина: `tests/test_readings.py` запускает отдельный процесс Uvicorn, который
наследовал окружение без `CGM_DATABASE_URL`. При таком запуске DB-конфигурация
по умолчанию использовала `data/cgm_assistant.sqlite3`; случайные уникальные
`run_id` предотвращали пересечение тестовых данных, но не запись в рабочий
файл.

Меры защиты:

- API-тестам теперь выделяется собственная временная директория и SQLite URL,
  который явно передаётся дочернему процессу Uvicorn вместе с
  `CGM_TESTING=1`.
- При `CGM_TESTING=1` неявный выбор БД в конфигурациях backend и модели Кирилла
  использует `CGM_DATABASE_URL`, если он задан, и иначе `sqlite:///:memory:`.
  Он не выбирает рабочую SQLite.
- Добавлен тест, который без `CGM_DATABASE_URL` проверяет безопасный in-memory
  fallback. API-тест также проверяет, что запись создала файл в отдельной
  временной директории, а не по рабочему пути.
- README указывает `CGM_TESTING=1` для запуска backend-тестов. Постоянные
  интеграционные тесты используют отдельные временные SQLite, тесты без
  постоянного хранения остаются in-memory.
- Backend/симуляторный набор повторно запускался два раза подряд с
  `CGM_TESTING=1` и удалённым `CGM_DATABASE_URL`: оба прогона завершились
  успешно, по 43 теста. Проверка test-mode в отдельном подпроцессе подтвердила,
  что backend и модуль БД Кирилла оба выбирают `sqlite:///:memory:` без
  `CGM_DATABASE_URL`.

Резервная копия текущего состояния рабочей БД создана до повторных проверок
через SQLite backup API (исходник открыт read-only):
`/tmp/cgm-assistant-workdb-before-test-isolation-20261114T0233+0300.sqlite3`.
Проверка копии: `PRAGMA integrity_check = ok`; SHA-256 копии
`a43c7c32a0cf831df52c2ef237172c007aab498b18c8615897c4889b5fa3548a`.
Исходный файл до и после создания копии имел SHA-256
`a1c0c45ed8204d49723d40bc516c47f240904ae57e26f4c85171a480e0ccb0e8`.
Копия сохранена и не удалялась.
После повторных тестов SHA-256 рабочей БД остался
`a1c0c45ed8204d49723d40bc516c47f240904ae57e26f4c85171a480e0ccb0e8`;
число записей во всех основных таблицах совпало с резервной копией.

## Ограничения

- UTC использован только как явно заданное техническое допущение. Для
  содержательной интерпретации времени требуется подтвердить часовой пояс
  исходной выгрузки.
- Анализатор и уведомления являются демонстрационными. Результаты не
  предназначены для принятия медицинских решений и не заменяют штатные
  предупреждения CGM.
- Проверена production-сборка frontend; визуальная проверка Dashboard в
  браузере в рамках этого прогона не выполнялась.
