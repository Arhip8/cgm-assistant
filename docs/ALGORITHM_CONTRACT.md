# Контракт интеграции демонстрационного анализатора событий

## Источник алгоритма и ограничения

Backend вызывает готовую функцию
`external/hackathon_event_analyzer/event_analyzer.py::analyze_measurement`.
Исходник алгоритма и его демонстрационные пороги не изменяются. Алгоритм
предназначен только для демонстрации, не является медицинским инструментом и
не должен использоваться для подавления или задержки штатных предупреждений
CGM.

Функция принимает `measurement`, `history`, `state`, `rules` и возвращает
словарь со статусом обработки, метриками, массивом событий и `next_state`.

## Вход анализатора

- `measurement` — словарь, преобразованный из API-модели `Reading`:
  `run_id`, `source_index`, `measured_at`, `glucose_mmol_l`.
- `history` — до пяти предыдущих корректных измерений того же запуска,
  упорядоченных по исходному времени по возрастанию. Текущее измерение в
  список не входит.
- `state` — состояние, возвращённое предыдущим вызовом для того же `run_id`,
  либо `None` при первом вызове. Backend хранит состояние отдельно для каждого
  запуска и передаёт копию, не разделяя изменяемый объект с алгоритмом.
- `rules` — результат `validate_rules()` исходного алгоритма. По умолчанию это
  его `DEFAULT_RULES`; значения остаются демонстрационными и не переопределяются
  адаптером.

Временная метка преобразуется из timezone-aware `Reading.measured_at` через
`datetime.isoformat()`. Значение глюкозы передаётся без изменения в
`glucose_mmol_l`.

## Результат исходного алгоритма

`analyze_measurement` возвращает объект следующей формы:

```json
{
  "status": "processed",
  "run_id": "demo-001",
  "source_index": 17,
  "measured_at": "2026-11-12T12:05:00+03:00",
  "glucose_mmol_l": 10.2,
  "metrics": {
    "delta_mmol_l": 2.2,
    "rate_mmol_l_min": 0.44,
    "minutes_since_previous": 5.0
  },
  "events": [
    {
      "event_id": "stable-event-id",
      "run_id": "demo-001",
      "event_type": "demo_above_range",
      "phase": "started",
      "origin": "demonstration_algorithm",
      "priority_hint": "info",
      "started_at": "2026-11-12T12:05:00+03:00",
      "measured_at": "2026-11-12T12:05:00+03:00",
      "ended_at": null,
      "glucose_mmol_l": 10.2,
      "details": {}
    }
  ],
  "next_state": {
    "run_id": "demo-001",
    "last_measured_at": "2026-11-12T12:05:00+03:00",
    "last_value_mmol_l": 10.2,
    "band": {},
    "trend": null,
    "rise_count": 0,
    "fall_count": 0
  }
}
```

Фактические значения `metrics`, `events` и `next_state` зависят от истории,
состояния и правил; пример иллюстрирует формат, не задаёт медицинских порогов.
Статусы алгоритма: `processed`, `duplicate`, `out_of_order`.

## Модель события API

Backend сохраняет каждое событие из `events`, в том числе несколько событий
одного измерения. API-объект события содержит:

| Поле | Значение |
|---|---|
| `event_id` | Идентификатор эпизода; при завершении сохраняется тот же ID, что и при начале. |
| `run_id` | Идентификатор запуска симулятора. |
| `event_type` | Тип демонстрационного события. |
| `phase` | `started`, `ended`, `interrupted` или `observed`. |
| `origin` | Источник события из результата анализатора. |
| `priority_hint` | Подсказка алгоритма, не медицинский приоритет и не уведомление. |
| `started_at` | Исходная временная метка начала. |
| `ended_at` | Временная метка завершения/прерывания, иначе `null`. |
| `measured_at` | Временная метка измерения, породившего запись события. |
| `glucose_mmol_l` | Значение измерения из события алгоритма. |
| `details` | Дополнительные демонстрационные сведения анализатора. |

Событие — запись о состоянии/фазе обнаруженного паттерна. Оно не является
информационным уведомлением: уведомления и Web Push в этой интеграции не
создаются.

## Жизненный цикл интеграции

После успешной валидации backend сериализованно записывает новое измерение,
собирает до пяти предыдущих измерений и запускает адаптер. При идентичном
повторе `run_id` и `source_index` API возвращает прежний HTTP 200 и анализатор
не вызывается. Конфликтующий повтор по-прежнему возвращает HTTP 409, ошибка
валидации — HTTP 422.

Для статуса `processed` backend сохраняет события и `next_state` данного
`run_id` в SQLite вместе с измерением, уведомлениями и состоянием серверной
политики. При статусах `duplicate` или `out_of_order` состояние и события не
меняются. При сохранном файле SQLite данные восстанавливаются после
перезапуска. Временное in-memory хранилище используется отдельными тестами.
Публичный режим Render Free допускает потерю файла БД; см. PUBLIC_DEMO.md.

События доступны через `GET /api/v1/events`, опционально с фильтром
`?run_id=demo-001`. JSON-контракт `POST /api/v1/readings` не меняется.
